# RCA — Fundle Brain / outreach SMTP send failures (smtp.office365.com:587)

**Deployment:** fundle-sales (`fundlecrm.fundle.ai` / `fundle-sales.emergent.host`)
**Active run:** 8838b6b8-89a9-489d-9032-f29819620056 (redeploy, success, completed 2026-11-12 19:26:07Z)
**Scope:** RCA only — nothing deployed or changed.
**DB read:** `fundle-leads-test_database`

## Symptom
In Fundle Brain chat (`POST /api/brain/sessions/{sid}/chat`, SSE), sending an intro email to the Go Colors contact (`vatsal.koolwal@gocolors.com`) from Abhinav's inbox failed with "Abhinav's email server timed out".

## Confirmed root cause
The production backend **cannot complete a TCP connection to `smtp.office365.com:587`**. Every send attempted after ~19:30 on 2026-11-12 fails at the SMTP *connect* stage with a timeout. This is a **network-reachability failure, not auth / credentials / app code** — the identical code, config and inbox sent 200 emails successfully earlier the same day.

### Evidence
1. **App-recorded error text** on failed `outreach` docs:
   `error: "Could not reach smtp.office365.com:587 in time — check server/port"` — i.e. a socket connect timeout to the O365 SMTP submission port. No SMTP 4xx/5xx and no auth-rejection (535) was recorded, so the failure is before the TLS/auth handshake.
2. **outreach docs with an `error` field** (3 total, all same error string):
   - Tattva Wellness Spa → `shipra@tattvaspa.com`, `status:approved`, `failed_via:0`, `failed_at:2026-11-12 19:32:03`, `send_attempts:1`.
   - Medkart → `debashish@medkart.in`, `status:approved`, scheduled 2026-11-11 (older).
   - Drunken Monkey → `sandeep@thedrunkenmonkey.in`, `status:approved`, scheduled 2026-11-11 (older).
   - No doc carried a `force_sender`. `sent_via`/`failed_via` for the implicated sends = **0**.
3. **Go Colors doc** (`vatsal.koolwal@gocolors.com`, id 2902): still `status:approved`, `email_status:pattern`, **no `error` / no `failed_at` persisted** — the chat SSE send timed out without writing the error back to the outreach doc.
4. **Inbox index 0 = Abhinav.** `settings.key=outreach` signature is "Abhinav Khanna, CBO | Fundle.AI"; `auto_send:true`, `daily_cap:200`.
5. **brain chat blocking on the connect** — `error_logs`: four `POST /api/brain/sessions/1/chat` entries 2026-11-12 19:31:26 → 19:36:32, all `kind:"slow"`, status 200, durations 9.5s / 21s / **50.2s** / 15.4s. The long blocks match a TCP connect timeout inside the send tool → surfaced to the user as "Abhinav's email server timed out".
6. **Backend stdout** carries no SMTP traceback (the app persists SMTP failures to the Mongo `error` field, not stdout; stdout is dominated by LiteLLM/Gemini logs, including Gemini 429 rate-limit noise — a separate concern).

## Are regular auto-outreach emails from inbox 0 sending? (last 24h)
**Yes, earlier — then it stopped and started timing out.**
- 200 `outreach` docs with `status:sent`, all `sent_via:0`, within the last 24h.
- All of them completed **on or before 2026-11-12 14:16:13**; exactly **200 sent on 11-12 before 14:16** = the `daily_cap:200`. So the 14:16 stop was the **daily cap (by design), not the bug.**
- `settings.key=status_reset` shows the daily counter **reset at 2026-11-12 18:31:07** (IST day rollover to 11-13).
- The **first send attempt after that reset — the 19:32 cron (`settings.outreach_last`: `sent:0, failed:1`)** — failed with the SMTP connect timeout. **0 emails have sent since 14:16:13.**
- `562` approved docs have a past `scheduled_at` and are now backlogged/unsent.

## Is port 587 to smtp.office365.com reachable from the production pod?
**Could not be authoritatively tested** — there is no exec-in-production-pod tool. A sandbox (eph) connect test is **non-representative and was discarded**: the `agent-eph` namespace egress is more restricted than the deployment namespace (it even timed out on 443 to the same host, whereas production reaches HTTPS/Gemini and reached O365:587 fine earlier today).
**Behavioral conclusion:** 587 WAS reachable from production earlier on 2026-11-12 (200 successful sends); it has been **timing out from the production pod since ~19:30 on 2026-11-12**.

## Correlation / likely trigger
The timeouts began immediately after the **19:26:07 redeploy produced a fresh pod**. Most plausible underlying causes (not individually provable with available tools):
- The new pod's egress / NAT source IP is being **blocked or connection-throttled by Microsoft O365** (possibly after the 200-send burst), or
- A cluster/network egress change on `deployment-cluster-03` affecting outbound 587, or
- A transient Microsoft 365 / Exchange Online service incident.
All are consistent with a *connect timeout* (vs an auth or SMTP protocol error).

## What is ruled out
- Not a secret/credential issue — the failure is at TCP connect, before auth.
- Not an app code/config regression — the same image/code/inbox sent 200 emails hours earlier.
- Not tier/OOM/manifest — no pod kills; app otherwise healthy and serving.

## Recommended actions
1. **Platform (Emergent):** Investigate production pod egress to `smtp.office365.com:587` on `deployment-cluster-03`. Timeouts started right after the 19:26 redeploy spawned a new pod — check whether the new node/NAT egress IP is firewalled or blocked/throttled for outbound 587.
2. **User → Microsoft 365 (third-party):** In Exchange Online admin, verify Abhinav's mailbox (sender index 0) isn't being connection-throttled or blocked for SMTP AUTH submission on 587 after the 200-send burst; confirm SMTP AUTH is enabled for the mailbox and check the M365 Service Health dashboard for an active incident.
3. **User → test & verify:** Retry a single send from Abhinav's inbox now and report whether it still times out — this distinguishes a transient O365 blip from a persistent egress block.

## Secondary (not root cause, optional)
- The Brain chat send has no short SMTP connect timeout and does not persist the failure onto the targeted `outreach` doc (Go Colors doc has no `error`), so a failed chat send is invisible in the outreach record and blocks the SSE request up to ~50s. Worth hardening in code later, but it is not the cause of the send failure.
