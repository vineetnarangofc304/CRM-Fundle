## TL;DR
The AI research provider is **Google Gemini**, accessed through the Emergent LLM proxy (litellm, `provider=openai`) using `EMERGENT_LLM_KEY`. Gemini is returning **HTTP 429 "You exceeded your current quota, please check your plan and billing details"** across the whole gemini model family (gemini-3.1-pro-preview, gemini-3-flash-preview, gemini-3.5-flash). The prospector retries down a fallback chain; when a model (gemini-2.5-flash / claude) has headroom it succeeds, so contacts are **still being produced intermittently** (153 in last 6h). But when the whole chain is throttled the contact run fails and returns 0 — **744 of 1834 contact runs have failed (~41%)**. This is an LLM quota/budget exhaustion, not an app crash. The app, crons and DB are healthy.

## Root cause
LLM quota exhaustion on **Google Gemini via `EMERGENT_LLM_KEY`** (Emergent LLM proxy). Gemini returns 429 "exceeded your current quota / check your plan and billing" for the gemini-3.x model tier the prospector prefers; ~41% of contact runs fail when the fallback chain is also throttled, which is what surfaces to the user as "0 new contacts". The application, crons, and database are otherwise healthy.

## Suggested fixes (not applied — read-only)
1. **LLM budget/quota (third party):** Top up / raise the Emergent LLM (`EMERGENT_LLM_KEY`) Gemini budget, or check plan & billing per the 429 message. This is the direct cause.
2. **Code (E1):** Reduce `prospecting.concurrency` (currently 10 — aggressive and self-inflicts the 429s) and/or reorder the model fallback to prefer models with headroom (claude-sonnet-5-5 / gemini-2.5-flash) as primary for the contacts phase, with exponential backoff on 429. Also tighten the discover timeout (one run burned 240s). This stops the burst failures without more quota.
3. **Code/config (E1):** Verify `/api/cron/prospecting-watchdog` is actually scheduled/routed — no execution observed; if it exists to unstick `contacts_status="running"` locks it is not doing so.
